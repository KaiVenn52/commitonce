**There is no pre-existing CommitOnce code to disclose.** Every first-party file in this
repository — both programs, the SDK, the tests, the examples, the demo, the scripts and all
documentation — was written inside the Contest Period. This is stated as a fact rather than a
reassurance, and §4 shows the timestamps it rests on.

leads with the finding that the receipt-PDA mechanism and the prepend-a-guard developer experience
are already deployed on Solana mainnet. Claiming either as an invention would be a
misrepresentation, and the submission does not.

| 15:00 | **the rent-exemption question is answered, and the answer is the runtime's** | last round I recorded as open whether real Agave refuses a transaction whose writable account is not rent-exempt — LiteSVM 0.16 does, and LiteSVM aims to match Agave, but that was inference. `apps/demo/rent-exemption-check.ts` settles it against `solana-test-validator` 4.2.2: deploy both programs, fund an attacker, have it send the victim's receipt PDA one lamport, then have the victim submit `claim`. The attacker's own transfer is refused — `InsufficientFundsForRent`, account never created — and the victim's claim then succeeds. **The rule is Agave's, not the harness's.** The distinction is worth keeping: "the attack is absorbed by our code" and "the attack cannot be built" are different claims, and only the first is guaranteed on a runtime without the rule, which is why the top-up path stays |
| 15:30 | and the script had three bugs before it measured anything | each was found by the run failing rather than by reading it. The attacker was funded and then read back at **zero** — `sendTransaction` returns a signature, not a confirmation, so the balance query raced the cluster; it polls now. The rejection was reported as bare `"AccountNotFound"` until the funding was actually checked, which would have been read as "the attack works" when it meant "the measurement never started". And the error formatter threw `Do not know how to serialize a BigInt` — the runtime error carries lamport amounts, so the naive `JSON.stringify` fails at exactly the moment it is needed. Three bugs, all in the measurement apparatus, none in the thing being measured |
| 16:00 | **the harness was accused of being wrong for two rounds, and it was right** | `EVIDENCE.md` said: *"the harness does not match the runtime: devnet reported `claim` at 14,669 CU against the harness's 9,283 median, so the in-process numbers are a lower bound."* I had repeated that for several rounds without ever checking it, because it sounded like appropriate humility. `apps/demo/cu-on-runtime.ts` reads the runtime's own per-program figures, and the answer is that the harness is **accurate**: `claim` costs **9,292 CU** on devnet (4.3.0-rc.0) and **9,292 CU** on a local `solana-test-validator` (4.2.2) — identical on two independent clusters — against a harness median of **9,283 CU**, within 0.1%. The 14,669 figure was taken on a build from **before the pre-funded-PDA fix and the CPI instruction** and was never re-measured when the program changed. A number that is never re-measured after the code changes is not evidence; it is a memory. Every table, the website, the SDK README and the project description now carry the measured figure |
| 16:30 | and the measurement script failed four times before it measured anything | the same pattern as the rent-exemption check, and worth recording because it keeps recurring. (1) A fixed idempotency key meant the second run found an existing receipt and reported `AlreadyCommitted` — a **rejected** transaction whose compute figure measures the failure, not the instruction. (2) `getTransaction` returns `{ meta, transaction }` and I passed the whole response where the meta was expected, so every figure came back `null`. (3) Preflight rejected the duplicate before it landed, so there was no meta to read at all — `skipPreflight` is required to measure a transaction that is *supposed* to fail. (4) The first version printed `rejected` alongside a CU number without saying the number was meaningless. **Four bugs, all in the apparatus.** The pattern is consistent enough now to name: the measurement is the hard part, and a check that silently measures nothing while reporting a plausible figure is the failure mode to watch for |
