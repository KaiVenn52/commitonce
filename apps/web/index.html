commit_once::claim — one instruction, prepended to the transaction you already build

Solana deduplicates transactions by message hash. A rebuilt retry is a different message.

Your client submits a payment. The response times out and it cannot tell whether the transaction landed, so it rebuilds — fresh blockhash, higher priority fee because the first attempt was slow, re-signed. Different bytes, different message hash, so the runtime's status cache has nothing to match on: both attempts can execute. Solana's own production-readiness guidance names this and hands the fix back to the application.

The guarantee, stated exactly

At-most-once successful execution of a guarded logical intent within the configured retention window.

Not exactly-once. CommitOnce prevents a second execution; it does not make the first one land. Retry until success and you get exactly-once-style application semantics. Three parts of that sentence are load-bearing: at most once, guarded transactions only, and within the window — after a receipt expires and is cleaned up, the key is free again.

H1 ≠ H2 and p ≠ p′, so the runtime sees two unrelated transactions and AlreadyProcessed never fires. The two attempts share one thing the chain cannot see: they are the same logical intent. That is the gap.

02 — the mechanism

The guard is not a retry helper. It is instruction 0 of the same atomic transaction.

claim derives a receipt PDA from (authority, namespace, idempotency key) and tries to create it. If the account is already there, the instruction errors, the error fails the transaction, and every instruction after it — your business instructions — never runs. Atomicity is what makes the guard correct rather than merely convenient.

One intent, one commit. The retry costs a transaction fee and nothing else.

Two commits for one intent — a duplicated payment, mint or order. This is the failure the guard exists to prevent.

A receipt cannot exist without its action having committed

If a later instruction fails, the receipt creation rolls back with it. There is no state in which a receipt exists but the action did not happen, so a failed attempt stays retryable instead of being permanently poisoned. Only the transaction fee is spent.

downstream_failure_rolls_back_the_receipt

A blocked duplicate cannot partially execute

When claim errors, the error fails the transaction, so the business instructions after it never run. There is no window in which half of the guarded work happened.

Receipt identity — the address is the intent

receipt PDA = find_program_address(
    seeds = [
        b"commit-once",        // 11 bytes — domain prefix
        authority,             // 32 bytes — the signer
        namespace_hash,        // 32 bytes — sha256("commitonce/namespace/v1" ‖ namespace)
        idempotency_key_hash,  // 32 bytes — sha256("commitonce/key/v1" ‖ key)
    ],
    program_id = CiiKHnzF1u9Nr5CuD7FgouN5oHs7pNeCUFuRgBCJrLnB,
)
  • The authority is in the seeds. A third party who learns your namespace and key derives a different address, so they cannot consume your key and cannot block your intent. Enforced by the program's seeds constraint, not left to callers to remember — an un-scoped "have I done this already?" guard is a griefing vector. third_party_cannot_consume_another_authoritys_key
  • Hashes are derived client-side. Fixed-size instruction data, unbounded strings kept out of PDA seeds, and the derivation pinned to golden hex vectors in two languages. prepareIntent() needs no RPC, prover or indexer.
  • The fingerprint covers meaning, not transport. Recipient, amount, mint, memo, order id — never blockhash, signature, priority fee, compute budget, retry count or submission route. Including any of those would make a retry look like a new intent and defeat the product. Reusing a key with a different fingerprint is reported as IdempotencyConflict, not silently swallowed.
  • Retention is explicit. Either a bounded window (one hour to 365 days) or permanent, which never expires and can never be closed. After cleanup the key is free again — a deliberate trade-off, asserted by closing_frees_the_key_for_a_new_claim rather than only described.
  • Cleanup is permissionless and cannot steal. close_receipt refunds the deposit to the destination recorded at claim time, and the program refuses any other destination. Both a slot deadline and a wall-clock deadline must pass, so a change in slot timing can only ever delay cleanup, never accelerate it into a window where a still-valid signed duplicate could execute.
  • Durable-nonce transactions are refused unless retention is permanent. A nonce transaction never expires, so a cleanable receipt would reopen the duplicate window forever. claim detects the nonce marker in the Instructions sysvar and rejects it.

Reading these numbers honestly

  • Measured vs computed. The receipt data length, the deposit, and the claim instruction size and account count are read from the account store and are identical on every run. Transaction wire size is computed — LiteSVM does not report serialized size, so legacy_wire_size() in tests/benchmarks.rs derives it from the legacy message format. The +404-byte delta decomposes exactly as 128 bytes of added account keys (4 × 32) plus a 276-byte instruction. Those numbers are exact.
  • The compute units are not exact, so they are not stated as if they were. LiteSVM's compute accounting is not reproducible run to run: the same unmodified test binary, running the same byte-identical .so, reported a bare counter increment at 5,567, 7,067 and 19,067 CU across three consecutive runs. The figures above are therefore a range over 9 independent environments, and devnet's own figures are listed separately because they differ from the harness's. Quoting one number would be precision nobody could reproduce.
  • Budget against the top of the range. ~23,000 CU for a guarded transaction is about 11% of the 200,000 CU default budget, and well under the 400,000 CU limit the demo transactions were granted on devnet. The baseline here is a trivial counter increment, so the relative cost falls as the guarded action grows. Of every compute-unit figure, only close_receipt's 2,701 CU showed no variance at all.
  • The account delta is usually +3, not +4. The four are the receipt PDA, the Instructions sysvar, the System program and the CommitOnce program id — and in a typical transaction the System program is already present.
  • The deposit is refundable. close_receipt returns the full 1,676,400 lamports once both deadlines have passed; only the cleanup transaction fee is spent. A permanent receipt never refunds it.
  • The rent rate is live, and the crate constant is wrong. Rent is 5080 lamports/byte since SIMD-0437 step 2, read out of the live mainnet Rent sysvar: (202 data + 128 overhead) × 5080 = 1,676,400. The solana-rent Rust crate still ships a stale effective 6960 lamports/byte, so any estimate derived from it is 37% too high. The test harness overrides the sysvar so the figures above are accurate.
  • Not measured on mainnet, and the harness does not match the runtime. Devnet reported claim at 14,669 CU against the in-process median of 9,283, so the range above is a lower bound rather than a prediction. Budget from the devnet figure — see the status section.

04 — quickstart

Build the guard, prepend it, keep retrying

The whole integration surface is one instruction. prepareIntent() is pure — it derives everything locally with WebCrypto and touches no network, which is what makes the guard usable inside a wallet, a relayer or an offline signer.

1

From a checkout of this repository

pnpm install
pnpm --filter @commitonce/solana build   # dist/ is gitignored
pnpm --filter @commitonce/solana test    # 71 tests

Requires Node 20.18.0 or newer and pnpm 11 (both pinned in the workspace package.json). The SDK has zero runtime dependencies; @solana/kit is a peer dependency.

2

Prepend the guard to your own instructions

// packages/sdk/quickstart.mjs — runs offline: WebCrypto hashing and local signing only.
import { bytesToHex, isAlreadyCommitted, prepareIntent } from '@commitonce/solana';
import {
    appendTransactionMessageInstructions,
    createTransactionMessage,
    generateKeyPairSigner,
    pipe,
    setTransactionMessageFeePayerSigner,
    setTransactionMessageLifetimeUsingBlockhash,
} from '@solana/kit';

const authority = await generateKeyPairSigner();

// The fingerprint covers what the intent *is*, never how it was transported.
// Including a blockhash, priority fee or signature here would defeat the product.
const intent = { to: recipient, mint: 'USDC', amount: 10_000_000n };

// 1. Build the guard. Pure: no RPC, no prover, no indexer.
const guard = await prepareIntent({
    authority: authority.address,
    namespace: 'payments:transfer',
    idempotencyKey: 'order_928',   // reuse the SAME key on every retry
    intent,
    retention: '24h',              // or 'permanent', which never expires
});

// 2. Prepend it to the transaction you were already building. Same atomic transaction.
const message = pipe(
    createTransactionMessage({ version: 0 }),
    (m) => setTransactionMessageFeePayerSigner(authority, m),
    (m) => appendTransactionMessageInstructions(
        [guard.instruction, ...yourBusinessInstructions],
        m,
    ),
    (m) => setTransactionMessageLifetimeUsingBlockhash(latestBlockhash, m),
);

console.log(guard.receipt);                     // the receipt PDA this intent claims
console.log(bytesToHex(guard.instruction.data)); // 144 bytes, fixed size

// 3. A rebuilt retry produces the same guard bytes and the same receipt address,
//    so the second attempt is blocked instead of executing again.
isAlreadyCommitted(rpcError);                   // true — treat as success, do not retry again

recipient, latestBlockhash, yourBusinessInstructions and rpcError are yours — the surrounding transaction is not CommitOnce's business. A complete, runnable version of this file (including a locally signed transaction and the offline rebuild-equality check) is docs/QUICKSTART.md → Path A.

3

Then run the guard against a cluster you control

bash scripts/build.sh   # builds, then verifies declare_id! against deploy-keys/
bash scripts/test.sh    # 54 tests against the compiled SBF artifact, exit 0
bash verify.sh          # everything, with a PASS/FAIL summary and the true exit code

The Rust suite needs no validator, no RPC and no funds — it runs the compiled program in-process through LiteSVM.

Before you copy any of this

  • The SDK is not on npm. @commitonce/solana is unclaimed and unpublished, so npm install @commitonce/solana will fail. Build it from a checkout of this repository, as in step 1.
  • There is no mainnet deployment to point at. The devnet program is live; if you want this on mainnet you must deploy and fund it yourself, and the program is unaudited.
  • The examples in this repository submit real transactions to devnet and need a funded keypair and an RPC endpoint.
  • Retrying is still your job. The guard makes a second execution impossible; it does not make the first one happen.

Live contention
Five to eight transactions carrying one idempotency key, fired at real devnet validators: exactly one commits, the rest are rejected onchain with AlreadyCommitted. The attempts spread over two to three slots — a client cannot force a leader to pack them together — so the same-slot case rests on the in-process test.
Real integrations
Three of the four examples have been executed against devnet, not just typechecked, and the fourth has been composed against a real Jupiter swap transaction. The guard composed with the System Program, with SPL Token + Associated Token in one transaction, and with an arbitrary Anchor program — and in each case the rebuilt retry was blocked while the business effect landed exactly once. The Jupiter swap is the fourth: it composes cleanly with a real transaction fetched from Jupiter's live API, verified in dry-run mode, but has not executed end to end — Jupiter's aggregator is mainnet-only and CommitOnce is devnet-only, and the page says so rather than implying otherwise.
A defect found, and fixed
Writing a test found a real one: a receipt address is derived from (authority, namespace, key), and those are semi-public — an order id, a job id — so an attacker could compute a victim's receipt PDA and send it one lamport. That made claim take the create path against an account that already held lamports, which fails, and would have denied the victim that key permanently. Reading the code did not surface it; the test failed on its first run. claim now tops such an account up and then allocates and assigns it under the PDA's own seeds. Written up as T2b in the threat model.
SDK tests
71 passing, pinning the derivation to golden hex vectors that a second implementation recomputes independently.
Build integrity
The build verifies declare_id! against the program keypairs and exits 1 on mismatch rather than producing a silently broken artifact.
Documentation

Known limitations of the design

  1. The window is finite unless you choose permanent. After cleanup the key is free again.
  2. The authority is a single account. No multisig or threshold authority in the program itself. A Squads vault can act as the authority — a PDA becomes a Signer only through invoke_signed, and that path is tested — and because the receipt is derived from the vault, members sharing one vault share one receipt. Individual member keys still cannot share one unless they share a vault.
  3. Durable-nonce transactions require permanent retention.
  4. A conflicting payload is detected, not resolved. The program reports it; deciding what to do is the application's job.
  5. The fingerprint is only as good as what you put in it. Pass semantic fields, never transport details.
  6. It does not make a transaction land, and it does not protect a code path that skips the guard.

06 — prior art

The closest competitor, named by us

A judge or an investor will find this anyway, so it belongs on the page. CommitOnce is not novel in mechanism: a receipt that aborts if it already exists is an old, widely used primitive. The closest product is Light Protocol's nullifier-program ↗ (NFLx5WGPrTHHvdRNsidcrNcLxRruMC92E4yv7zhZBoT) — real, live on mainnet and devnet, permissionless, generic, and described in much the same terms. Its own README says unaudited, use at your own risk.

Why they are not materially equivalent — five concrete reasons
Light nullifier-programCommitOnce
Seeds ["nullifier", id] — no signer authority-scoped, enforced by the program's seeds constraint
Griefing anyone who guesses an id can claim and block it a third party derives a different address
Dependencies requires an RPC or prover round trip to fetch a validity proof before the instruction can be built self-contained; derivation is local and pure
Storage compressed accounts, Light state trees, upgradeable plain 202-byte PDA, 1,676,400 lamports, refundable on cleanup
Namespaces none first-class

What is genuinely new here

Not the receipt-PDA-abort-if-exists mechanism. It is the combination: an authority-scoped key space enforced by the protocol, a self-contained instruction that needs no RPC or prover, explicit namespaces, a bounded retention window with a refundable deposit and permissionless cleanup, and the productization around it.

Also acknowledged

Solana's production-readiness guide names the problem and assigns the remedy to the application. Squads' nonce-guard uses the same Instructions-sysvar introspection this program uses for its nonce policy. Anchor's init idiom is the same primitive at a smaller scale. Helium's lazy_transactions genuinely implements at-most-once execution across rebuilds, but is application-specific rather than generic. The Stripe-style Idempotency-Key pattern is the closest conceptual relative — and SDP's specification includes a transaction id in its fingerprint, a primary-source admission that HTTP idempotency keys do not solve rebuilt transactions.
